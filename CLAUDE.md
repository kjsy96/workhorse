# Workhorse — Project Notes for Claude Code

This is a zero-build-step HTML/CSS/JS task and project management app, built incrementally across a series of chat sessions with Claude (claude.ai). It was called "Kanban Board" through v1.4, when it did only continuous Kanban-style boards; renamed to Workhorse ([issue #12](https://github.com/kjsy96/workhorse/issues/12)) once it grew Scrum mode alongside Kanban, since "kanban board" stopped describing what it actually does. As of v1.4 (issue #9's file split, then Scrum mode itself, issue #8), the app is split across a handful of plain files rather than one single HTML file — see the table below — but it's still zero-build/zero-dependency and still opens by double-clicking `workhorse.html`. This file exists to hand off full project context to Claude Code, since chat memory doesn't carry over automatically between products. Read this whole file before making changes — several sections document real bugs and their fixes, and repeating them is a real risk if this history isn't taken into account.

**A note on the rename:** everything below that describes the *current* state of the project (this section, "Project basics," "Current state" at the end, and any present-tense technical fact) uses the new name and filenames. The "Feature history" section further down is a chronological narrative of what actually happened in each past version — it's left referring to `kanban.html`/`kanban-core.js`/etc. throughout, since that's genuinely what the app and its files were called at the time each entry was written, and rewriting 15 entries of dense historical prose to retroactively say "Workhorse" would be needless transcription risk for a purely cosmetic change. Mentally substitute the new filenames (see the table below) when a historical entry references a file by its old name.

## Project basics

- **Nature:** zero-build-step, zero-dependency app split across `workhorse.html`/`workhorse.css`/`workhorse-core.js`/`workhorse-render.js`/`workhorse-scrum.js` (see the file table above) — no bundler, no npm dependencies, no `<script type="module">`. The only external resource is two Google Fonts loaded via CDN link tags (Fraunces, IBM Plex Sans/Mono). Runs by double-clicking `workhorse.html` and opening it in a browser — **this is why the JS files are loaded as plain `<script src>` tags, not ES modules**: Chrome/Edge block module `import`/`type="module"` script loading from `file://` URLs (a CORS-style restriction), which would silently break the double-click-to-open workflow. Plain scripts have no such restriction, and since classic (non-module) `<script>` tags in the same document share one global scope, `workhorse-core.js`'s top-level `let`/`const`/`function` declarations are directly visible to `workhorse-render.js`/`workhorse-scrum.js` with no `window.` exporting needed, as long as `workhorse-core.js` loads first.
- **Please preserve the zero-build-step nature** unless Kevin explicitly asks to restructure the project (e.g., adding a bundler or framework). Splitting into more plain files following the pattern above is fine; introducing a build step or `type="module"` is not, without asking first.
- **Target browsers:** Chrome and Edge only. The app uses the File System Access API for autosave, which Firefox/Safari don't support. This is called out in the app UI itself ("works in Chrome or Edge only").
- **Owner:** Kevin, building this for personal task management (Windows). He's also shared a copy of the app with a friend for their own independent use (separate file, no shared data).
- **Communication style:** prefer plain English over jargon. Explain *what* you're about to do and *why* in layman's terms before running commands, rather than assuming familiarity with git, npm, or terminal conventions.

## Development workflow (professional GitHub flow — follow for EVERY change, no exceptions)

Starting with issue #2, every unit of work on this project — feature, bug fix, or update, no matter how small — goes through this full cycle. Kevin explicitly asked for this to mirror professional software development practice; there is no "too small for this" exception (a one-line typo fix still gets an issue, a branch, and a PR). Do this without being re-asked each time.

1. **File a GitHub issue first**, via `gh issue create`, before writing any code. Claude Code files the issue itself from Kevin's description — he doesn't need to write it separately. Use the repo's issue templates (`.github/ISSUE_TEMPLATE/`: `bug_report.md` or `feature_or_update.md`) as the shape to follow, and label appropriately (`bug` / `enhancement`).
2. **Create a branch off `master`** named `<issue-number>-<short-slug>` (e.g. `12-fix-newline-bug`).
3. **Commit normally** as work progresses, matching this repo's existing commit style (a descriptive body explaining *why*, not just *what* — see the git log for examples).
4. **Actually verify the change before opening the PR** — open it in a real browser, check the console, exercise the specific feature/fix. This project has a real history of bugs that "looked right" but weren't (see Feature History below); don't skip this step or treat reading the diff as equivalent to running it.
5. **Open the PR** (`gh pr create`) using `.github/PULL_REQUEST_TEMPLATE.md`'s shape: a Summary, `Closes #<issue-number>` (so merging auto-closes the issue), and a Test plan documenting what was actually verified in step 4.
6. **CI runs automatically** — `.github/workflows/ci.yml` runs a Playwright smoke test (`tests/smoke.spec.js`) on every PR and push to `master`: loads `workhorse.html` headlessly, asserts zero console/page errors, and exercises a basic add-a-task interaction. This is a real, meaningful check, not decorative — it was verified during setup to actually fail when the app is broken (a deliberately-injected `ReferenceError` was confirmed to fail both test cases before being reverted). A PR should not be merged with a failing CI run.
7. **Kevin reviews, tests, and explicitly approves before any merge.** Never merge on your own judgment alone, even if CI is green and you're confident — "this looks ready to me" is not the same as his go-ahead. Ask in chat and wait for a clear yes, exactly like the v1.3 PR.
8. **Merge squash-style** (matching the v1.3 precedent) and delete the branch. Confirm the linked issue actually closed (via the `Closes #N` text in the PR body).
9. **Bump the version badge/tag/release** per the versioning convention below, when the merged change is significant enough to warrant a new version — trivial fixes can batch under the next meaningful version rather than each getting their own release.

**CI tooling note:** `package.json`, `package-lock.json`, `playwright.config.js`, and `tests/` exist solely to run the CI smoke test — they do NOT change how the app itself runs. `workhorse.html` and its supporting files remain zero-build-step and dependency-free for actual use (see "Project basics" above); `node_modules/`, `test-results/`, and `playwright-report/` are gitignored. Running the smoke test locally requires Node.js (installed via `winget install --id OpenJS.NodeJS.LTS` during setup, since this machine didn't have it) — `npm install && npx playwright install --with-deps chromium && npx playwright test`.

## Versioning convention (CHANGED — read this before assuming the old rule still applies)

**Historical convention (v1.0 through v1.2):** every update was saved as a NEW file (`kanban-v1.0.html`, `kanban-v1.1.html`, `kanban-v1.2.html`) rather than overwritten in place, so old versions stayed archived. `kanban-v1.0.html` and `kanban-v1.1.html` are preserved as-is in `Archive/` (`Archive/kanban-v1.0-test-empty.html` is a disposable test copy, safe to delete). `kanban-v1.2.html` was **not** separately archived — when the switch to git-based versioning happened, it was `git mv`'d directly to become the current `kanban.html`, so its content lives on as the base of the current file rather than as a frozen copy. **One documented exception during the old convention's era:** v1.0 received an in-place hotfix (see "v1.0 hotfix" below) for a critical startup-crash bug discovered immediately after release, rather than being bumped to a new version file — a judgment call treating it as "fixing v1.0 to actually be v1.0" rather than a feature change.

**Current convention (from v1.3 onward):** this project now has a real git repository and a public GitHub remote (`kjsy96/workhorse`), so the manual file-per-version scheme has been retired in favor of normal git tags/commits, exactly as this section used to recommend. Practical implications:
- Edit files **in place** going forward — do not create `workhorse-v1.5.html`, etc. There is only ever one live copy of the app at the repo root (`workhorse.html` plus its 4 supporting files).
- When a meaningful set of changes ships, bump the in-app version badge (`<span class="version-badge">` in `workhorse.html` and the `APP_VERSION` const in `workhorse-core.js`) to the next version number, commit, then create a matching git tag and GitHub Release with notes (mirroring how v1.0 through v1.4 releases were already done — see the [Releases page](https://github.com/kjsy96/workhorse/releases)). v1.3 also introduced using a PR (rather than pushing straight to `master`) for the first time — see "Development workflow" above, which formalizes this as the standing process for every change from here on.
- `Archive/` is now purely historical (pre-git files) and won't gain new entries going forward — new "versions" live in git history/tags instead of new files.
- This change was discussed with and approved by Kevin (not assumed unilaterally) after v1.3's features were implemented directly in-place, which is what prompted formalizing the switch.

## Feature history (chronological)

1. **Base kanban board** — three fixed columns (To do / In progress / Done), drag-and-drop cards between columns, add tasks via a textarea per column, localStorage persistence, IBM Plex Mono/Sans + Fraunces serif for headers. Editorial/paper aesthetic (`--paper`, `--ink`, `--line` CSS variables).
2. **Card editing** — hover-activated edit affordance, `contentEditable` text with Shift+Enter for newlines (implemented via `execCommand('insertText')` with manual Range API fallback — plain Range manipulation alone was unreliable), Enter to save, Escape to cancel and revert.
3. **Undo/redo** — in-memory history stacks (50-step limit), header buttons + Ctrl+Z/Ctrl+Y/Ctrl+Shift+Z. `pushHistory()` snapshots `JSON.stringify(state)` before mutations. Native browser text-undo still works while a field is focused (global undo listener explicitly ignores keydowns when `document.activeElement` is a contentEditable or textarea).
4. **Multi-project support** — the board expanded from one flat list to multiple named "projects," each with its own To do/In progress/Done columns, switchable via pill-style tabs at the top. Tabs support: click to switch, double-click to rename (inline contenteditable), `+` to add a new project, `×` to delete (with confirm dialog, undoable). Tasks can be moved between projects via a per-card menu, keeping the same column status across projects.
   - **Data model:** `state = { projects: [{ id, name, todo: [], doing: [], done: [] }], activeProjectId }`.
   - Old single-board localStorage data auto-migrates into a "My Tasks" project on first load.
5. **Deadlines (optional per task)** — native `<input type="date">` inside a per-card menu. Badge shown in the card footer when set; turns red/"overdue" styling if the date has passed and the task isn't in Done.
   - **Bug fixed:** initially, the date input's `change` handler called a full `render()`, which destroyed and rebuilt the DOM on every keystroke (because editing an *existing* date value re-validates to "complete" after every digit typed, firing `change` repeatedly). This yanked focus out of the field mid-type, making it impossible to type a 4-digit year. Fixed by decoupling the data update from any destructive re-render — the change handler now updates state and a small in-place badge directly, with only one `pushHistory()` call per edit *session* (tracked via a `focus`-reset flag), not one per keystroke.
6. **Kebab (⋮) menu** — all per-card actions (Edit, Deadline, Move to project, Delete) were consolidated from separate always-hoverable icons into a single kebab icon in the top-right of each card, visible only on card hover, opening a dropdown panel.
   - **Bug fixed in two passes (same root cause):** the dropdown kept getting visually hidden behind the card below it.
     - *Pass 1:* Root cause identified as `.card:hover` applying a `transform`, which creates a new CSS stacking context; since sibling cards had no explicit `z-index`, a card lower in the DOM order could still paint on top of an earlier card's entire stacking context (including its dropdown). Fixed by giving `.card` an explicit baseline `z-index: 1` and bumping it on `:hover` to `z-index: 5`.
     - *Pass 2:* This wasn't quite enough — the dropdown could stay open after the mouse moved away from the card (e.g., drifting toward the next column), at which point `:hover` no longer applied and the z-index boost disappeared while the menu was still visually open. Fixed by adding a separate `.menu-open` class (toggled in JS, independent of `:hover` state) bumped to `z-index: 6`, so an open menu stays on top regardless of where the mouse currently is.
   - **Lesson for future menu/popover work:** any dismissible UI element that can remain open independent of `:hover` needs its own explicit stacking state — don't rely on `:hover` alone to keep something visually on top.
7. **Inline mixed formatting (bullets + checkboxes)** — rather than a whole-card format toggle (which was the first implementation and was explicitly rejected by Kevin in favor of this), formatting now lives *per line* inside the task's raw text, using a lightweight markdown-like syntax the user types directly:
   - `* text` or `- text` → bullet point (consecutive bullet lines auto-group into one `<ul>`)
   - `[] text` → unchecked checkbox
   - `[x] text` or `[X] text` → checked checkbox
   - any other line → plain text
   - When not editing, the raw text is parsed (`parseLine()`) and rendered as mixed plain/bulleted/checkbox content in a `.card-list-view` container; checkboxes are clickable directly (no need to enter edit mode) and toggling one flips the `[ ]`/`[x]` marker directly in the underlying text (`toggleCheckboxLine()`).
   - When editing (via the kebab menu's "Edit task"), the raw markdown-style text is shown for direct editing in the plain `.card-text` contentEditable box.
   - The earlier whole-card `listType` ('text'/'bullet'/'checklist') + separate `checked` boolean array data shape is auto-migrated into the new inline-syntax format on load (see `migrateItem()`), so old saved boards don't lose data.
8. **File System Access API — real autosave to disk** — the most significant architectural addition. Previously the app only used `localStorage`. Now:
   - A save-file menu in the header (see item 9 below for its current, corrected form) lets the user connect a `.json` file on disk that the app keeps in sync with.
   - The chosen `FileSystemFileHandle` is persisted in **IndexedDB** (`kanban-fs-db` / `handles` object store, key `saveFile`) so the connection survives page reloads.
   - On load, the app checks `handle.queryPermission()` silently (no user gesture needed for a *query*, only for an actual *request*); if permission was already granted, it silently reconnects and loads the file's content, overriding `localStorage`. If permission needs re-confirmation, the UI shows a red "save file disconnected" / "Reconnect" state, since re-granting permission requires a user gesture (a click).
   - All writes are serialized through a simple promise queue (`writeQueue`) to avoid overlapping `createWritable()` calls.
   - `localStorage` is still written on every `save()` call as an instant-loading fallback/cache, but the connected file (when present) is the authoritative source of truth going forward.
9. **v1.0 hotfix — startup ReferenceError (entire app broken, not just the save-status UI)**
   - **Symptom Kevin reported:** opening v1.0 showed "checking save file…" stuck forever in the header, with no button ever appearing. What wasn't immediately obvious: the *entire board* had also failed to render — no cards, no columns populated — because the failure happened before `render()` was ever reached.
   - **Root cause:** `save(state)` was called once synchronously at script startup (`let state = load(); save(state);`), and `save()` calls `queueFileWrite()`, which reads the `fileHandle` variable. But `fileHandle` was declared with `let fileHandle = null;` *textually after* that `save(state)` call. Unlike `var` or function declarations, `let`/`const` bindings are not accessible before their declaration line executes (the "temporal dead zone") — so this threw an uncaught `ReferenceError: Cannot access 'fileHandle' before initialization`, which silently killed the rest of the script, including the later `render()` call at the bottom of the file.
   - **Fix:** moved the File System Access `let`/`const` variable declarations (`fileHandle`, `pendingHandle`, `fileHandleNeedsPermission`, `writeQueue`, and the IndexedDB constants) to *before* the `let state = load(); save(state);` lines.
   - **This was verified**, not just visually inspected — the fix was run through a Node.js DOM-stub harness that executes the actual script and confirms it no longer throws, before being shipped.
   - **General lesson:** when adding new top-level `let`/`const` state that's read by a function called synchronously during script init, declare that state *before* the call site, not after. This bug class (TDZ ordering) is easy to introduce when incrementally adding features to code that already has synchronous init calls near the top of the file.
10. **v1.1 — critical data-loss bug fix.** A real data-loss incident occurred with v1.0: connecting to an existing `kanban-data.json` resulted in the file being silently overwritten with a blank board, destroying the saved data. Kevin had a manual backup, so it was recoverable, but the underlying bug was real and dangerous.
    - **Root cause:** the original single "Connect save file" button used `showSaveFilePicker()` (the "Save As" dialog) even when the intent was to *load* an existing file. This dialog is not guaranteed to hand back a faithful read of an existing file's prior bytes — it's semantically a write-intent dialog. Separately, `loadFromFileHandle()` had a design flaw: if the file's content failed to parse as recognizable board data for *any* reason, it assumed the file must be brand-new/empty and wrote the current (blank) in-memory state over it — destroying whatever was actually there, with no distinction between "genuinely empty" and "has real content I don't understand."
    - **Fix:**
      - `loadFromFileHandle()` now only auto-writes if the file is genuinely empty/whitespace-only. If it has real content that fails to parse, it refuses to touch the file, disconnects, and returns `false` so the caller can alert the user — it never silently destroys data.
      - The single ambiguous button was split into two explicit actions behind a small dropdown menu: **"Load existing file…"** (uses `showOpenFilePicker()`, the correct read-oriented API, then requests readwrite permission afterward for ongoing autosave) and **"Create new file…"** (uses `showSaveFilePicker()`, intended only for brand-new files — and even this now warns/confirms before overwriting if the chosen file unexpectedly already has content).
      - `reconnectSaveFile()` and `initFileConnection()` (the automatic reconnect-on-load path) were updated to use the same safe `loadFromFileHandle()` and handle failure gracefully.
    - **This was verified** with unit tests (not just visual inspection) against three cases: realistic backup data (must load successfully), genuinely empty content (must be treated as safe-to-seed), and garbage/corrupted content (must be refused, never written over). All three behaved correctly before shipping.
    - **This is the current, correct save-file behavior — see item 8 above for the general architecture, and treat this item as the authoritative description of the actual button/menu behavior in the current file.**
11. **v1.2 — done-column stacking, card truncation, night mode.** Three independent UI/UX additions, implemented and verified one at a time.
    - **Done-column card stacking:** once the "done" column has more than `DONE_STACK_VISIBLE_COUNT` (4) cards, cards 5+ collapse into a clickable "stacked paper" widget (`.done-stack`, offset `::before`/`::after` pseudo-elements for the peek effect) reading "+N more done"; clicking it expands to full individual cards plus a "Show less" button. Expand state is ephemeral (in-memory `expandedStacks` Set keyed by project id — never persisted, resets on reload). The widget and collapse button are deliberately non-`.card` elements always appended last in the dropzone, so the existing drag-and-drop index math (which assumes `.card` elements are direct children of the dropzone in array order) is untouched — dropping near a collapsed stack simply appends to the end of the array, which was already `moveItem()`'s existing fallback behavior for an `undefined` target index.
    - **Card text truncation:** long cards clamp to a fixed height (`.card-list-view.clamped`, `max-height: 190px` with a bottom fade gradient) rather than counting raw `\n` characters — an initial version counted newlines only (`item.text.split('\n').length > 8`) and missed cards with just a couple of long *wrapping* paragraphs (few raw newlines, many visual lines); the fix measures actual rendered `scrollHeight` via `requestAnimationFrame` (since a card's list-view isn't attached to the DOM yet at the moment it's first built) and compares against `TRUNCATE_CLAMP_HEIGHT`. The "Show more"/"Show less" toggle button is a sibling of `.card-list-view`, not a child, so it's never clipped by the clamp's `overflow: hidden`. All content is always fully rendered in the DOM (only visually clipped when collapsed), which sidesteps any concern about checkbox line-index alignment.
    - **Night mode toggle:** new header button (next to Undo/Redo) switches `:root` CSS variables via `[data-theme="dark"]`. Defaults to `prefers-color-scheme` on first visit, then remembered via a dedicated `kanban-theme-v1` localStorage key — deliberately **separate** from board `state`/`STORAGE_KEY`/`pushHistory()`, so toggling the theme never enters undo history and never gets written into the user's connected save-file JSON (mirrors how the File System Access handle already lives in its own IndexedDB store alongside board data, rather than inside `state`). A small synchronous script in `<head>` (before the `<style>` block) applies the saved/OS theme before first paint, to avoid a flash of the wrong theme. ~9 previously-hardcoded colors (ink-tinted hover overlays, the red "danger" text/backgrounds for delete actions and overdue deadlines) were converted to new `--overlay`/`--danger`/`--danger-bg`/`--danger-wash` variables so they theme correctly too.
    - **This was verified** by driving the app's real code paths directly via the browser console (dispatching real DOM events against the actual input/checkbox/button elements, not just visual inspection) — boundary cases for both stacking (3/4/5/6+ done cards) and truncation (short cards, many-short-lines, few-long-wrapping-lines, checkbox state past the visible fold) all confirmed correct, plus confirmed theme toggling never touches `undoStack`/`redoStack` or the connected save-file's JSON contents.
    - Superseded `kanban-v1.1.html`, which is now archived (see the file inventory table above) rather than edited in place, per the versioning convention that was in effect at the time.
12. **v1.3 — save-file warning modal, drag-to-tab, mobile/touch support.** The first version implemented directly in place in `kanban.html` rather than as a new versioned file — see "Versioning convention" above for why that changed.
    - **No-save-file warning modal:** a persistent, non-dismissible `.save-warning-backdrop`/`.save-warning-modal` overlay appears whenever `fileHandle` is null and `supportsFS` is true — covering both "never connected" and "needs reconnect" (permission expired) states, matching the two existing branches already in `updateSaveFileStatus()`. A new `fileConnectionChecked` flag (set as the first line inside `initFileConnection()`) gates the modal so it never flashes on load for users who are already validly connected — the modal-visibility check only runs after the real connection state is known, not during the synchronous pre-check call that happens before `initFileConnection()`'s async work resolves.     - **Follow-up bug fix — newlines erased when editing an existing card:** reported as "insert a new-line, add more text, save, and the newlines are erased with everything bunched together." A same-line fix using the built-in `.innerText` was tried first and rejected — verified live that it double-counts a trailing empty `<div><br></div>` line (4 newlines for what should be 2), so the hand-rolled walker was used instead, specifically handling that "div containing only a `<br>`" case as exactly one line break rather than two.
    - **This was all verified live**, not just read from code: reproduced the exact reported repro (edit an existing card → Shift+Enter → type more text → save) via real DOM events dispatched against the actual `.card-text` element, confirmed the saved text now preserves the newline correctly, and separately re-tested a card with existing bullets/checkboxes to confirm multi-line edits with markdown-lite syntax still save correctly across an edit session.

13. **v1.3.1 — drag-over flicker on the last tab in a wrapped row.** The first bug fixed through the project's new issue-driven workflow (see "Development workflow" above): filed as [issue #4](https://github.com/kjsy96/workhorse/issues/4), fixed on its own branch, verified live, shipped via [PR #5](https://github.com/kjsy96/workhorse/pull/5).

16. **v1.4 — Scrum mode.** [Issue #8](https://github.com/kjsy96/workhorse/issues/8): a per-project toggle between Kanban and a sprint-based Scrum workflow, so a project can be a lightweight Kanban board or a Backlog/Sprint/Review-Test/burndown setup, side by side with other projects, without touching either the existing Kanban rendering path or previously-saved data. Scope was deliberately narrowed with Kevin before implementation (see the issue and its first comment): stays single-user/local-file (no backend), Kanban and Scrum are the full set of workflow types (no generic "workflow engine"), one program rather than a separate lite/robust pair, and the same CSS design system throughout — no new visual language.
    - **The core trick: `COLS` became the zone list, not just the 3 Kanban columns.** `const COLS = ['backlog', 'todo', 'doing', 'review', 'done']` (`kanban-core.js`). Because `findItem`/`moveItem`/`moveItemToProject`/`removeItem`/`renderBoard`'s per-item closure/both drag-and-drop paths all already iterate `COLS` generically, Backlog and Review became fully drag-and-drop-, edit-, and delete-capable for free — no parallel logic anywhere. The Backlog/Review columns exist in the static HTML *unconditionally* for every project (hidden via `.column[data-col="backlog"], .column[data-col="review"] { display: none; }`, shown via a `.board.mode-scrum` class), never conditionally injected — the one-time drag-and-drop wiring loop does an unguarded `getElementById('dropzone-' + col)` at top-level script scope, so a missing element there would throw and silently kill the rest of the script, the same bug class as the v1.0 TDZ crash (item 9 above). A project's `todo`/`doing`/`review`/`done` arrays represent the whole Kanban board in Kanban mode and *the active sprint's board* in Scrum mode — sprint metadata (name/goal/dates) lives separately in `proj.activeSprint`, item arrays are never nested inside it, so only one genuinely new interactive drop zone (Backlog) was needed; sprint history is a read-only archive, not another live drop target.
    - **Mode switching (`toggleProjectMode` in `kanban-scrum.js`):** Kanban→Scrum with existing tasks shows a `confirm()` (mirroring `deleteProject()`'s existing "...you can undo this with Ctrl+Z" wording) and moves them into the Backlog; an empty board switches with no prompt. Scrum→Kanban is always just a visibility change — no confirm, no data movement, so an in-progress sprint is frozen and resumes exactly where it was left if switched back. `migrateState()` backfills `mode`/`backlog`/`review`/`sprints`/`activeSprint` onto existing saved projects (array/object fields need an explicit backfill since pushing into `undefined` throws; `item.points` needed none, same as `deadline` — every read site already treats a missing value as unset).
    - **Sprint lifecycle:** Start Sprint opens a modal (name, optional goal, required start/end dates, a checklist of current Backlog items to include) and moves the selected items into To do; `unit` (`'points'` vs `'count'`) and `startingTotal` are decided once, at that moment, so the burndown chart's "ideal" line has a fixed reference even if items are added to the backlog later mid-sprint. Complete Sprint confirms, archives the sprint's metadata plus its Done items into `proj.sprints` history, returns unfinished To do/In progress/Review items to the Backlog, and clears the board for the next sprint. Sprint history reuses the existing `.done-stack` collapsed-widget pattern rather than inventing a new one.
    - **Story points (`item.points`, optional):** available on every card in *both* modes, not Scrum-gated — deliberately mirrors the `deadline` kebab-menu block exactly (same row/label markup, `refreshPointsUI()` mutating the existing badge node in place, a focus-armed `pushHistory()`), since that pattern is what fixed this codebase's one real "typing loses focus" bug (item 5 above) and any new input risks reintroducing it if it calls `render()` from its own `change` handler instead.
    - **Burndown chart:** hand-rolled inline SVG (no chart library), built as an HTML string and fully rebuilt on every render — safe here since, unlike the points/deadline inputs, a chart has no focus state to preserve. `upsertTodayBurndownPoint()` runs from inside `renderProjectToolbar()` (not hooked into `moveItem`/`removeItem`, keeping that shared chokepoint untouched), recomputes "remaining" from the current To do/In progress/Review contents on every render, and find-or-replaces *today's* `burnHistory` entry rather than appending one per render; it's derived telemetry, so it calls `save()` but deliberately never `pushHistory()`. All strokes/fills reference CSS variables (`var(--todo)` etc.), not hardcoded hex, so the chart themes correctly in dark mode.
    - **A real gotcha hit mid-implementation, worth remembering for future multi-PR work:** squash-merging a PR and deleting its branch (this repo's standard merge flow) auto-*closes* — not retargets — any other open PR that was stacked on top of that branch, because a squash merge rewrites history and the stacked PR's commits are no longer reachable from the new `master`. No work was lost (the stacked branch still has every commit locally), but the fix was a clean `git cherry-pick` of the stacked PR's commit(s) onto the fresh `master` and a new PR — not a rebase or a retarget, both of which would have shown a bloated/duplicate diff. After hitting this once, later PRs in the same feature were branched directly off `master` instead of stacked, specifically to avoid it recurring.
    - **Also fixed along the way:** a toolbar/board alignment bug (`.project-toolbar` and `.board.mode-scrum` each had their own wider max-width for the 5-column Scrum layout, pulling them out of alignment with `.project-tabs`) — everything now shares the same 1160px max-width in both modes, and Scrum's columns are simply proportionally narrower instead of the board growing wider.
    - **This was verified live, not just reasoned about** — and, as with issue #9's reorg, the in-app browser preview tool available during this work session could not execute this local multi-file app (same "static snapshot" limitation), so verification used this project's own Playwright setup against real Chromium throughout: the pre-existing smoke tests plus new committed tests covering mode-toggle-with-data-move, the full start-sprint→drag-through-Review→complete→history→reload-persists flow, story points (including typing a multi-digit value character-by-character specifically to catch the historical focus-loss bug class), and the burndown chart (including injecting synthetic multi-day `burnHistory` data directly via the console, the same technique used historically for v1.2's done-stack boundary testing, plus the zero-item-sprint edge case). ## Important correction: local file:// storage is SHARED, not per-file

Earlier guidance in this project assumed `localStorage` was scoped per exact file path, and that opening a differently-named HTML file would start with a blank slate. **This was wrong and has been empirically disproven.** In Chrome/Edge, local `file://` pages share a single storage origin — `localStorage` AND `IndexedDB` (where the connected save-file handle is stored) are shared across **every** local HTML file opened from disk, regardless of filename or folder. Confirmed by testing: opening a freshly-named test copy (`kanban-v1.0-test-empty.html`) in the same browser showed both the existing task data (from shared `localStorage`) and found the previously-connected file handle (from shared `IndexedDB`, surfaced as a "save file disconnected/Reconnect" prompt needing a fresh permission click).

**Practical implications:**
- Switching between versioned files in the same browser/profile likely carries data over automatically — no manual export/import needed in that case.
- To test anything (like the file-connect flow) against a genuinely blank slate, use an Incognito/InPrivate window, which gets an isolated storage partition. A differently-named file in a normal window will NOT be isolated.
- The manual `localStorage` copy/paste-to-JSON workaround (below) is really only needed as a last resort when moving to a genuinely different computer/browser profile AND there's no existing exported `.json` save file to use instead.

## Migrating to a genuinely new browser/computer (no shared storage)

**Preferred method (if a `.json` save file already exists, e.g. `kanban-data.json`):** just copy that file to the new machine and use "Load existing file…" in the app's save-file menu. This is the safe, tested path (see v1.1 fix above) and requires no console work.

**Fallback method (only if data exists solely in browser localStorage, with no exported `.json` file):**
1. In the source browser, open DevTools Console on `workhorse.html` and run `copy(localStorage.getItem('kanban-personal-board-v1'))` to copy the raw JSON state to clipboard — note the storage key itself is unchanged by the Workhorse rename (see "Nature" above: display name and internal identifiers are deliberately decoupled), so it's still `kanban-personal-board-v1` even now.
2. Paste it into a plain text file, save as `workhorse-data.json` (with "All Files" type in Notepad to avoid a forced `.txt` extension).
3. On the new machine/browser, open `workhorse.html` and use "Load existing file…" to select that file.
